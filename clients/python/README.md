# clearance-core-client

The Python client of the Clearance core's HTTP API (`contract/clearance-core.json`). Built: the Autopilot gateway
calls the core through it from R-3 on. Standard library only (no runtime dependencies), Python 3.11+.

```python
from clearance_client import CoreClient, CoreUnavailable, CoreRequestError, EvaluationRequest

core = CoreClient(
    "http://clearance-core.clearance-system:8080",
    token_file="/var/run/secrets/tokens/clearance",  # re-read on every request (projected SA token)
    provider="autopilot-gateway",
)
try:
    res = core.evaluate(EvaluationRequest.from_dict(request))  # or a plain dict
except CoreUnavailable:
    ...  # the outage policy: fail closed, fast
if res.decision:
    ...  # apply res.context.spend, act, then:
    core.outcome(res.decision_id, {"result": "ok"})
else:
    ...  # a deny: res.context.rule, .message, .hint

core.record("session.open", {"session": "s-1", "task_id": "t-1", "principal": "user:alice",
                             "agent": "coding-agent", "result": "opened"})
```

`AsyncCoreClient(...)` has the same methods as coroutines (each runs in a worker thread, so the event loop never
blocks on the core). Methods: `evaluate`, `outcome`, `record`, `publish_definitions`, `register_change`,
`clear_change`, `deny_change`, `verify_provenance`, `healthz`, `readyz`; property `breaker_state` (`closed`, `open`,
`half-open`). `publish_definitions(pins, rejected)` replaces the core's cluster-pinned agent definitions with the
provider's whole set (`PUT /v1/definitions`, a provider registered with `definitions: true`); a whole set can be
large, so a caller may give it a client with a longer `timeout` than the decision path's.

## Errors

A deny is a result (`decision` False), never an exception. Every exception is a `ClearanceClientError`:

| Exception | When | Breaker |
|---|---|---|
| `CoreUnavailable` (`reason`: `breaker_open`, `connection`, `timeout`, `server_error`; `status`, `attempts`) | the breaker is open, the connection failed, an attempt timed out, or a 5xx after the retry | counts |
| `CoreRequestError` (`status`, `message`, `rule`, `hint`) | a 4xx: the request is wrong or not allowed | resets (the core answered) |
| `BadResponse` | an answer that does not fit the contract (strict decoding), an unexpected status, an oversized body | resets |
| `TokenUnavailable` | the token could not be read; nothing was sent | unchanged |

## Outage policy

The defaults are the policy decided on 2026-11-02 (spec R-3); every one is a `CoreClient` argument:

| Argument | Default | Meaning |
|---|---|---|
| `timeout` | `0.25` | seconds per attempt, connect to last byte |
| `retries` | `1` | retries of a retryable failure, at once |
| `breaker_threshold` | `5` | consecutive unavailable calls that open the breaker (`0`: no breaker) |
| `breaker_cooldown` | `5.0` | seconds an open breaker fails calls fast before one probe goes through |
| `max_response_bytes` | 4 MiB | answer body cap |
| `allow_unknown_fields` | `False` | accept an answer with fields this client does not know (a rolling upgrade only) |

What is retried depends on whether the call is safe to repeat. `evaluate`, `publish_definitions` (the same set
again records nothing), `register_change`, `verify_provenance` and the probes: any connection failure, timeout, 502, 503 or 504. `outcome`, `record`,
`clear_change`, `deny_change`: only a failed connect (nothing was sent) or a 503 (the core did not record), so a
record is never written twice and an outcome that did land is not turned into a 409. A 500 is never retried.
`healthz` and `readyz` bypass the breaker. A half-open breaker lets exactly one probe through; its success closes
the breaker, its failure opens it for another cooldown.

## Generated, and versioned with clearance

`src/clearance_client/_models.py` (dataclasses for every schema in the contract, the operation table) and
`_version.py` are generated by `go run ./tools/pyclient` from the module root; never edit them. The Go test
`tools/pyclient` fails when they are stale, so a change to the core's types or routes carries the regenerated
client in the same PR. Answers are decoded strictly: an unknown field, a missing required one or a wrong JSON type
is `BadResponse`.

The version is the clearance release: the generator reads `[project].version` of the repo's root
`pyproject.toml`, which is the version the `vX.Y.Z` tag names. When the Python core leaves the repo (R-3), or
clearance#42's CHANGELOG.md becomes the release source, change `ReleaseVersion` in `tools/pyclient` to read that
instead; the version bump PR runs the generator.

## Tests and the release

```sh
cd clients/python && pip install -e '.[test]' && pytest -q
```

The tests run a real core: they `go build ./cmd/clearance` (or use `CLEARANCE_BIN`) and start
`clearance core --memory --insecure-dev-auth` on a free port. CI: the `python-client` job in
`.github/workflows/go.yaml`, which also builds the wheel.

For whoever wires the release workflow (R-8): on a `v*` tag, build with `uv build clients/python` (or
`python -m build clients/python`), check that the wheel's version equals the tag without its `v`, and attach
`clients/python/dist/*.whl` and the sdist to the release. Autopilot then pins
`clearance-core-client @ https://github.com/jfillman/clearance/releases/download/vX.Y.Z/clearance_core_client-X.Y.Z-py3-none-any.whl`
(or a git URL with `#subdirectory=clients/python`) by the same tag.
